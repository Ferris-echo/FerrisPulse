## 二、原生层做了什么

反汇编 `UsbServer_ReadBatteryLevel`（RVA 0x102D0）和 `UsbFinder_GetBatteryLevel`（RVA 0xD540）：

```asm
; 组包：命令 0x0408，长度 0x10
mov word ptr [rsp+0x38], 0x408
call 0xF060                  ; 发 HID 命令
call 0xC970                  ; 收响应
; 取 4 个字节原样返回
movzx eax, byte ptr [rsp+0x26]   ; → 输出[0] 电量%
movzx eax, byte ptr [rsp+0x27]   ; → 输出[1] 充电标志
movzx ecx, byte ptr [rsp+0x28]   ; → 输出[2] 电压高位
movzx eax, byte ptr [rsp+0x29]   ; → 输出[3] 电压低位
shl cx, 8 ; or cx, ax            ; → 输出[2..3] 电压 mV
```

**原生层没有任何计算**——只做 HID 收发和 4 字节拷贝。

## 三、电压表的下落

电压表 `3050, 3420, ..., 4110`（21 个 int32）存在于两处：

| 位置 | 地址 | 是否被代码引用 |
|---|---|---|
| hidusb.dll 数据段 | RVA `0x230AC` | **扫描全部 `lea`/`mov` rip 相对指令，±16 字节范围内零引用** |
| Mouse Drive Beta.exe | 文件偏移 `0x4E8668` | 不在 FieldRva 表里；全文件搜 `ldc.i4 3050` **零命中** |

结论：**这张表在运行时没有被任何代码读取**，只是用于首次生成 `Config.ini` 的模板值。

## 四、C# 层没有电压换算

- 全程序集搜 `ldc.i4 3050 / 3420 / 4110 / 370 / 12` —— 在电量相关类型里零命中
- `FieldRva` 只有 2 项，且都是哈希命名的字段，与电压表无关

## 五、结论：官方不用电压法

综合以上，官方驱动的电量百分比**直接来自设备上报的固件电量计**（`rxBat[6]`），电压只用于界面显示。

这解释了所有实测现象：

| 场景 | 官方 | 固件计（我们读到的） | 电压法（我们） |
|---|---:|---:|---:|
| 充电 3.850V | 41% | 50% | 44% |
| 放电 3.775V | 37% | — | 36% |

官方 41% 既不是固件计的瞬时值（50%），也不是电压法（44%）——**说明官方对固件计做了平滑/滞后处理**。

## 六、对我们实现的意义

| 项 | 判断 |
|---|---|
| 我们的电压法 | **比官方更接近真实**（官方全程滞后于固件计） |
| 官方"与电压法一致"的印象 | 错觉——只是碰巧在低电量段两者接近 |
| 继续追官方数值 | **没有意义**，官方本身就是滞后的 |

之前两次按官方显示值反推表格（3050→3200→3150）都错，根因就是：**把一个滞后的读数当成基准去校准精确的算法**。
